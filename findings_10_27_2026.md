# Findings: 27 October 2026

*Kumo Relational (NVIDIA's pretrained relational foundation model) vs. tuned XGBoost on cancer data.*

For background on the models, datasets, metrics and protocol, written for non-specialists, see [`RESULTS.md`](RESULTS.md). This file records **what we found**, including the fine-tuning and leaderboard work done after `RESULTS.md` was written.

**Status:** complete. The overnight run (3 fine-tuning seeds, XGBoost re-tuned, final leaderboard-set evaluation) finished at 00:26 UTC on 28 Oct; see [Overnight run results](#overnight-run-results-completed-0026-utc-28-oct).

---

## Headline findings

1. **With zero training, Kumo Relational matches a thoroughly tuned XGBoost**, on two datasets and three comparisons, using seconds of compute instead of hours. The margins are small (about the size of split-to-split noise).
2. **Fine-tuned Kumo reliably beats tuned XGBoost on held-out data**: 0.666–0.681 vs 0.733 log loss on the 368-row stage-1 test set across three random seeds, 7–9% lower. Fine-tuning takes 1–2 minutes on one GPU.
3. **On the Kaggle leaderboard set, every model does worse than guessing** (fine-tuned Kumo 3.30, XGBoost 3.34; guessing 2.197). The leaderboard rows have a radically different class mix from the training data. A standard label-shift correction does not fix it and hurts when there is no shift.
4. **Feeding Kumo its intended input format made no difference, and adding neighboring mutations hurt.** In the intended format, each example has its own copy of its linked rows. The model sees labels only on the row being predicted, so it cannot "borrow" labels from related rows.

## 1. Baseline comparison (no training for Kumo; XGBoost tuned with nested cross-validation)

| Comparison | Metric | Kumo Relational | XGBoost (tuned) |
|---|---|---|---|
| Breast cancer, 15 test splits | AUC | **0.9968** | 0.9948 |
| | Accuracy | **0.978** | 0.967 |
| | Log loss | **0.067** | 0.085 |
| Cancer mutations, 5 test splits | Log loss | **0.841** ± 0.045 | 0.854 ± 0.034 |
| | Accuracy | 0.694 | **0.703** |
| | Macro AUC | **0.932** | 0.926 |
| Cancer mutations, stage-1 test set (368 rows) | Log loss | 0.731 | 0.731 |
| | Accuracy | 0.723 | **0.731** |
| | Macro AUC | 0.920 | **0.938** |
| Compute, 5-split comparison | Wall time | ~20 s on one A100 GPU | 46 min on 30 CPU cores |

On the 5 mutation splits, Kumo had the lower log loss on 4 of 5: 0.819 / 0.843 / 0.906 / 0.853 / 0.784 vs XGBoost's 0.839 / 0.877 / 0.881 / 0.871 / 0.801.

## 2. Tuning Kumo's own settings

All settings were chosen by 5-fold cross-validation on training rows only.

| Configuration | Log loss |
|---|---|
| Mutation → gene only, 32 ensemble members | **0.843** |
| Mutation → gene only, 8 members (default) | 0.846 |
| Also include up to 20 other mutations of the same gene | 0.904 |
| Also include up to 5 other mutations of the same gene | 0.918 |

- **Defaults are near-best.**
- **Why neighbors hurt:** the model attaches labels only to the row being predicted, so neighboring mutations contribute features but not their known classes, and those features are mostly noise.
- **What it means for future work:** to exploit "mutations in the same gene or article tend to share a class," known labels must be written into the tables as data. XGBoost could be given the same features, so that would not by itself favor Kumo.

## 3. Fine-tuning Kumo

The package has no fine-tuning function, but the model supports gradients, so we wrote an **episodic** training loop. Each step:

1. randomly splits the fine-tuning rows into about 1,000 labeled "examples" and 256 "targets",
2. has the model predict the targets, and
3. nudges the weights to reduce log loss.

Settings: AdamW optimizer, learning rate 1e-5, about 2.5 steps per second on an A100.

**Protocol (stage-1 never used for any choice):**

1. Fine-tune on 80% of the training rows, checking the other 20% every 50 steps.
2. Take the best step count, then re-fine-tune from the original weights on all training rows.
3. Score once on stage-1.

| Step | Held-out training-row log loss |
|---|---|
| 0 (pretrained) | 0.816 |
| 100 | 0.789 |
| **200 (best)** | **0.780** |
| 400 | 0.784 |
| 600 | 0.787 |

**Result on stage-1:**

| Stage-1 (368 rows) | Log loss | Accuracy | Macro AUC |
|---|---|---|---|
| XGBoost (tuned, 100 candidates) | 0.731 | **0.731** | **0.938** |
| Kumo, pretrained | 0.731 | 0.723 | 0.920 |
| **Kumo, fine-tuned 200 steps** | **0.683** | 0.723 | 0.929 |

The gain comes mainly from better-calibrated probabilities (log loss), not from more correct top guesses (accuracy unchanged). Fine-tuning took about 1.5 minutes of GPU time.

## 4. The Kaggle leaderboard set (stage-2)

The competition's final leaderboard was scored on 125 labeled rows. 1st place scored 2.030. Guessing 1/9 for every class scores 2.197, and only 14 teams beat that.

**Why it's so hard:** the leaderboard rows' class mix is nothing like the training data.

| Class | Training | Stage-1 | Stage-2 (leaderboard) |
|---|---|---|---|
| 1 | 17% | 26% | 4% |
| 2 | 14% | 13% | **42%** |
| 7 | 29% | 27% | **4%** |
| 8 | **0.6%** | 0.5% | **26%** |

**Label-shift correction does not help.** We used a standard method (EM, Saerens et al. 2002) that estimates the test set's class mix from the model's own predictions on the 986 *unlabeled* stage-2 rows. It needs no labels.

- **It hurt on stage-1,** where there is little shift: Kumo 0.683 → 0.761, XGBoost 0.731 → 0.850. It sharpened predictions toward the majority classes.
- **It cannot see the real shift.** It estimated about 0–1% class 8 in stage-2, when the real figure is 26%, because the models almost never predict class 8 for these rows. This is a change in *what the rows look like*, not just in *how common each class is*, and reweighting can't fix that.

**Stage-2 scores for Kumo** (125 labeled rows; lower is better; these are worse than guessing):

| Model | Raw | Label-shift adjusted |
|---|---|---|
| Kumo, pretrained | 3.41 | 9.53 |
| Kumo, fine-tuned | 3.28 | 3.17 |

**Disclosure:** these Kumo stage-2 numbers were seen during a dry run of the final script, before the planned single final evaluation. **The stage-2 labels have therefore been looked at.** No modeling choice has been made from them, and none should be. The final script includes a clearly labeled *diagnostic* showing how much blending toward uniform each model would have needed on stage-2. It explains the leaderboard but is **not** a valid result and must not be used to pick a submission.

## 5. Practical findings

- **Environment:** on macOS, pip-installed PyTorch and conda-installed XGBoost load two copies of the OpenMP library and crash. Installing every compiled package from conda-forge fixes it (`setup_env.sh`).
- **XGBoost tuning speed:** this dataset is small, so one XGBoost fit gains little from many threads. Running many single-threaded tuning trials in parallel was about 5× faster than sharing a GPU among 4 trials. Running all 5 outer folds at once took the nested CV from an estimated 2.5 hours to 46 minutes.
- **Kumo on GPU vs laptop CPU:** about 8× faster on an A100 (20 s vs 157 s for 5 splits). It also runs fine on an Apple-silicon CPU.
- **Kumo input gotcha:** prediction columns come back named by class label in no guaranteed order. Always look them up by name.

## Overnight run results (completed 00:26 UTC, 28 Oct)

### Fine-tuning gain is reliable across random seeds

| Stage-1 (368 rows) | Best step (chosen on training rows) | Log loss | Accuracy | Macro AUC |
|---|---|---|---|---|
| **Kumo fine-tuned, seed 0** (pre-chosen official model) | 150 | **0.681** | 0.728 | 0.931 |
| Kumo fine-tuned, seed 1 | 200 | **0.680** | 0.731 | 0.932 |
| Kumo fine-tuned, seed 2 | 500 | **0.666** | 0.723 | 0.934 |
| XGBoost, re-tuned (100 candidates) | – | 0.733 | 0.726 | **0.943** |
| *(earlier runs: Kumo pretrained / XGBoost)* | – | *0.731 / 0.731* | | |

- **Every fine-tuning seed beats tuned XGBoost by 0.05–0.07 in log loss** (about 7–9%).
- **Accuracy is about equal,** and **XGBoost still ranks classes slightly better** (AUC 0.943 vs 0.931–0.934).
- So fine-tuned Kumo's advantage is in **probability quality**: its confidence better matches how often it's right, which is what the competition metric rewards.

### Final stage-2 (leaderboard set, 125 labeled rows)

All models learned from training + stage-1 rows. Lower is better; 1st place on the leaderboard was 2.030, and guessing 1/9 scores 2.197.

| Model | Raw | Label-shift adjusted |
|---|---|---|
| Kumo pretrained | 3.455 | 8.486 |
| Kumo fine-tuned (seed 0) | **3.300** | 2.866 |
| XGBoost (tuned) | 3.339 | 6.103 |

- **Raw scores:** fine-tuned Kumo is best, but all three are far worse than guessing.
- **The label-shift adjustment is erratic.** It helped fine-tuned Kumo (3.30 → 2.87) but made the other two much worse. It also **hurt every model on stage-1** (Kumo 0.681 → 0.761, XGBoost 0.733 → 0.804). There is no valid basis for choosing to apply it, so **the raw score is the honest result**.

**Diagnostic only** (it uses the stage-2 labels, so it is *not* a valid result): blending each model's probabilities with "1/9 for every class" at the best weight, chosen by looking at stage-2, gives:

| Model | Best weight on 1/9 | Log loss |
|---|---|---|
| Kumo pretrained | 0.85 | 2.168 |
| Kumo fine-tuned | 0.83 | 2.162 |
| XGBoost | 0.83 | 2.160 |

Even with that hindsight, every model only *barely* beats guessing (2.197), and all fall short of 1st place (2.030). The leaderboard set mainly rewards predicting its unusual class mix, which nothing in the training data reveals. **It cannot tell these models apart.** The stage-1 set and the cross-validation splits are the meaningful comparisons.

### Submission files

`data/msk/submissions/` holds 6 CSVs, one per model × raw/adjusted, in Kaggle's format (986 rows, `ID,class1..class9`). **None has been uploaded.** If one is submitted, the defensible choice, picked by the pre-stated rule rather than by stage-2 scores, is `kumo_fine_tuned_raw.csv`. Expect a leaderboard score around 3.3.

### Updated headline

Fine-tuned for about 1–2 minutes on one GPU, Kumo Relational **reliably beats a thoroughly tuned XGBoost on held-out data** (stage-1 log loss 0.666–0.681 vs 0.733 across three seeds). With no fine-tuning, it matches XGBoost. On the Kaggle leaderboard set, no model, ours or nearly all original competitors', does better than guessing. That set's class mix differs so much from the training data that it isn't a useful benchmark for comparing models.
